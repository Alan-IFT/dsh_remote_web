`dsh-remote-web` 是一个 DeepSeek Harness 插件。装上之后，你电脑上的 DSH 会**主动向外**连接到一台你自己部署的中转服务器；之后在任何地方打开浏览器，输入令牌，就能继续使用同一份会话、工作区和工具。

它不修改 DSH 源码，也不在你的电脑上开放任何入站端口。

## 能做什么

- **随时随地访问**：手机、平板、公司电脑，任何浏览器都行，界面就是 DSH 原本的网页界面。
- **不用公网 IP、不用端口转发**：家庭宽带、公司内网、酒店 Wi-Fi、NAT 后面都能用。
- **中转服务器完全自建**：不依赖任何第三方服务，数据只经过你自己的机器。
- **双令牌**：**认证令牌**决定"谁能连"(中转校验，只存公钥)，**加密令牌**把浏览器凭据绑定到某台机器——中转无法独自签发可用凭据。
- **你自建的中转，就是你信任的那一环**：它终结 TLS，因而能看到明文会话，请把它跑在你自己控制的机器上。浏览器内加密改变不了这一点，[原因见此](docs/DECISIONS.md#browser-side-end-to-end-encryption-was-removed)。
- **令牌只上网一次**：首次登录后改用签名认证，所以中转即使没有 HTTPS，也不会泄露可重用的凭据。
- **令牌可随时吊销**，吊销后**下一个请求**立即失效。
- **最小暴露面**：只转发 DSH 的网页界面，终端等敏感通道一律拒绝转发。

## 快速开始

装好后，**每台机器各粘贴一条命令**即可用。

### 1. 在你的服务器上

```bash
npm i -g github:Alan-IFT/dsh_remote_web
dsh-remote-web relay --host 127.0.0.1 --port 8787 --trust-proxy --url https://relay.example.com
```

在终端里跑,首次启动会**自动注册一台主机**,并打印下一步要执行的完整命令——不需要额外的注册步骤。前面套一层 HTTPS（[部署示例](#部署中转服务器)在下面）。

> 若是以服务方式启动（systemd、Docker）,则不会打印配对码:那里的输出会进日志,而配对码里带着中转服务器绝不该留存的加密令牌。这时它会提示你去跑 `agent add`——在终端里一次性显示,不写进日志。

> `--url` 填你的公网地址——它会被编进配对码,决定你的电脑连到哪里。

### 2. 在跑 DSH 的电脑上

先装插件,再粘贴上一步打印的命令:

```bash
dsh plugin --profile web add github:Alan-IFT/dsh_remote_web
dsh-remote-web setup dshrw1.....        # ← 从服务器复制
```

`setup` 完成后会直接打印**浏览器配对码**。打开中转地址、粘贴,就连上了。运行中的 DSH 几秒内自动生效,不用重启。

> 仓库自带编译产物,装完即用。配对码只显示一次,它携带这台电脑的签名密钥和加密令牌——中转两者都不保存。

### 之后要加设备

```bash
dsh-remote-web client add 平板 --agent <机器名>   # 在服务器上
dsh-remote-web invite <上一步打印的 token>        # 在电脑上
```

> `<机器名>` 就是注册时那台机器的名字（默认取主机名）。忘了可以 `agent list` 查。

两步分开是有意的:中转能发认证令牌,但**拿不到加密令牌**——所以它无法独自签发可用凭据。

## 工作原理

```
   你的电脑（NAT 后面）              你的服务器                    任何浏览器
┌──────────────────────┐      ┌──────────────────┐        ┌──────────────┐
│  DSH  127.0.0.1:3080 │      │   中转服务器      │        │              │
│         ▲            │      │                  │        │   浏览器      │
│         │ 回环请求    │      │  ┌────────────┐  │        │              │
│  ┌──────┴────────┐   │      │  │ 令牌校验    │  │        │              │
│  │ dsh-remote-web│───┼──────┼─▶│ 会话管理    │◀─┼────────┼── HTTPS ─────┤
│  │    插件        │   │ 主动 │  │ 帧转发      │  │  HTTPS │              │
│  └───────────────┘   │ 外连 │  └────────────┘  │        │              │
└──────────────────────┘      └──────────────────┘        └──────────────┘
      不开放任何端口              唯一需要公网的机器
```

1. 插件启动后，用 WebSocket **主动连出去**到中转服务器，并用 **Ed25519 签名**证明身份（私钥不出本机，中转只有公钥）。
2. 浏览器带令牌登录中转，换取一个 `HttpOnly` 会话 Cookie。
3. 浏览器的每个请求由中转打包成协议帧，经隧道送到你的电脑。
4. 插件在本机把请求**重新发起**一次到 `127.0.0.1:3080`，把响应原样送回去。

因为连接是电脑主动发起的，所以中间隔着多少层 NAT 都无所谓。

## 安全模型

这是一个能操作你电脑的入口，所以每一层都按“默认拒绝”设计。

### 双令牌:把"能连"和"能读"分开

一个令牌同时管两件事,就意味着中转握着解密所需的一切。所以拆成两个,**缺一不可**:

| | 认证令牌 | 加密令牌 |
|---|---|---|
| 主机形式 | Ed25519 密钥对 | 256 位随机数 |
| 中转存什么 | **只存公钥** | **什么都不存** |
| 管什么 | 谁能连接 | 谁能读内容 |

- **主机用签名认证**:私钥不出本机,中转只有公钥。**拿到中转的磁盘也冒充不了主机**。
  > 这一条是修出来的。早期版本用"存哈希 + 拿哈希当 HMAC 密钥",导致哈希本身就是可用凭据——我写了 PoC 确认能仅凭状态文件冒充主机,然后才改成非对称签名。
- **加密令牌永不上网到中转**:`agent add` 时生成,只经配对码交到你手上,之后只在你的电脑和你授权的浏览器之间使用。

### 中转能看到什么

中转**终结 TLS**，因此它看得到你的会话明文。这是自建反向代理的固有性质，不是缺陷。

本项目曾提供浏览器内端到端加密以规避这一点，**现已移除**。原因：执行加密的 JavaScript 由中转自己下发，而该功能的前提恰恰是"中转不可信"——恶意中转只需下发一份会泄露令牌的脚本。这是浏览器加密的经典困境，SecureDrop 的结论是"若你不信任服务器保管秘密，就不能信任它下发安全代码"；他们的解法 WEBCAT 需要浏览器扩展加透明日志，页面内无解。详见 [docs/DECISIONS.md](docs/DECISIONS.md#browser-side-end-to-end-encryption-was-removed)。

**因此请把中转跑在你自己控制的机器上。** 仍然成立的保证：

- 中转**存不到**机器签名私钥（只存公钥），无法冒充你的电脑。
- 中转**独自签发不了**可用的浏览器凭据——那需要只有你电脑持有的加密令牌。
- 隧道与浏览器之间全程 TLS；令牌只过网一次，之后靠签名认证。


### 认证

### 只转发该转发的

- **WebSocket 白名单**：只放行 DSH 的两条事件流 `/api/events.mux`、`/api/events.host`。终端、插件自己的 socket 一律拒绝——远程浏览器不应该拿到一个 shell。
- **插件不开任何 HTTP 接口**：开关和状态都走文件（`$DSH_HOME/remote-web/`，权限 `0600`），不存在可以被远程请求命中的控制接口。这是设计取舍，原因见下面“实测发现的问题”。
- **路径检查**：`..`、`%2e%2e`、`//` 开头等一律拒绝，原始和解码后各查一遍。
- **特权方法由 DSH 自己拒绝**:隧道**不伪装成回环**,而是以具名权威 `dsh-remote-web.internal` 出现。DSH 的栅栏本就区分"回环(可用特权)"和"具名受信主机(仅普通方法)",所以 `credentials.*`、`settings.*`、`host.openPath` 等全部由 DSH 用它自己的名单拒绝——**本插件不维护任何副本**。
  > 早期版本伪装回环 + 自己维护黑名单,审计时实测漏掉了 `llm.discoverModels`。改成具名权威后,DSH 未来新增特权方法会**自动被拒**。

### 请求头改写

DSH 自带一道防 DNS 重绑定的栅栏：只接受 `Host` 是回环地址、且 `Origin` 与之匹配的请求。远程浏览器的请求头显然过不了这一关。

插件的做法是**在本机重新发起请求**，而不是转发原始请求头：`Host`/`Origin` 改写成本机地址，同时把 `x-forwarded-*`、`forwarded`、`via`、`sec-fetch-site` 等所有可以伪造的“信任线索”**全部丢弃**。

这样做是安全的，因为身份认证发生在更早的地方：能走到这一步，说明中转已经验过令牌了。改写没有额外授予任何权限，只是把一个已授权的请求，用本机的身份重新说一遍。

### 三个不做的事

- 不做端到端加密（依赖 HTTPS）。中转服务器理论上能看到明文——但它是**你自己的机器**。如果你的威胁模型里连自己的服务器都不能信，参考 [deepseek-harness-remote](https://github.com/liguobao/deepseek-harness-remote) 的 Noise 方案。
- 不做 P2P / WebRTC 打洞，所有流量走中转。简单、可预测、在对称 NAT 下也能用；代价是带宽走你的服务器。
- 不提供多用户隔离。每个令牌能访问它被授权的电脑的全部内容，适合个人使用。

## 远程能用什么、不能用什么

对照本机真实 DSH(含 `dsh-better-sidebar`、`dshmarket` 等第三方插件)实测:

| 功能 | 远程 | 说明 |
|---|---|---|
| 对话、会话列表、模型选择 | ✅ | 事件流 `events.mux`/`events.host` 已放行 |
| 工作区、技能、子代理、任务、计划 | ✅ | 走普通 `/api` 转发 |
| 目录选择器 | ✅ | 本机装的是 `directory-picker-browse`(浏览器内浏览) |
| 图片/附件上传 | ✅ | 请求体上限 160 MiB |
| **侧边栏终端** | ❌ | WebSocket 白名单只放行两条事件流——**远程浏览器不应拿到 shell** |
| **设置 / 凭据面板** | ❌ | `settings.*`、`credentials.*` 属特权方法,只限本机 |
| **在主机桌面打开文件** | ❌ | `host.openPath` 属特权方法,远程调用只有滥用价值 |
| 移动端适配 | ⚠️ | 用的是 DSH 原生界面,**没有做手机适配**;小屏体验取决于 DSH 自身 |

后三项是**有意为之的安全取舍**,不是缺陷。若你需要远程终端,应当直接用 SSH,而不是让这个通道去承载它。

## 常用命令

在**你的电脑**上：

```bash
dsh-remote-web status         # 看隧道状态
dsh-remote-web disable        # 临时关闭远程访问
dsh-remote-web enable         # 重新打开
dsh-remote-web show-config    # 看配置在哪（不显示任何密钥明文）
dsh-remote-web invite <token> # 把中转发的令牌合成浏览器配对码
```

在**中转服务器**上：

```bash
dsh-remote-web agent list                 # 有哪些电脑
dsh-remote-web agent revoke <机器名>       # 踢掉一台电脑（立即断开）
dsh-remote-web client add 平板 --agent <机器名> --ttl 24    # 24 小时后过期
dsh-remote-web client add 手机 --agent <机器名>             # 绑定到指定电脑
dsh-remote-web client list                # 有哪些令牌（只显示指纹）
dsh-remote-web client revoke <id|指纹>     # 吊销令牌，立即生效
```

## 部署中转服务器

### Docker Compose（推荐，自动 HTTPS）

```bash
cd deploy
RELAY_DOMAIN=relay.example.com docker compose up -d
docker compose exec relay dsh-remote-web agent add 我的电脑 --state /data/state.json
```

Caddy 会自动申请和续期证书。见 [`deploy/docker-compose.yml`](deploy/docker-compose.yml)、[`deploy/Caddyfile`](deploy/Caddyfile)。

### systemd + 现成的反向代理

见 [`deploy/dsh-remote-web-relay.service`](deploy/dsh-remote-web-relay.service)（带完整的沙箱加固）和 [`deploy/nginx.conf`](deploy/nginx.conf)。

> nginx 配置里 `proxy_buffering off` 和 `Upgrade`/`Connection` 两组设置不能省，否则界面能打开但收不到实时消息。

### 不用 TLS？

`--no-tls` 只适合完全可信的内网或 VPN 里用。加了这个参数会打印警告，因为令牌和所有流量都是明文。

## 配置项

插件通常不需要配置。需要时可以在 profile 的 `cordis.patch.yml` 里写：

```yaml
- id: remote-web
  config:
    enabled: true        # false 彻底停用插件
    localPort: 8080      # 手动指定本机 DSH 端口（默认自动识别）
    maxRetryMs: 60000    # 断线重连的最大间隔
```

`localPort` 默认取 DSH 实际监听的端口，所以用 `--port` 或者同机跑多个 DSH 都不用管。

## 实测发现的问题

这个插件是对着真实 DSH 实例测出来的。发现问题后，我优先改设计而不是打补丁——下面每一条的修法都让**同类问题不可能再出现**，而不是挡住这一次：

1. **吊销令牌不生效**：中转是长期进程，`revoke` 是另一个进程；中转缓存了旧状态，不但看不到吊销，还会在下次写入时**把吊销覆盖掉**。
   *修法*：抽出 `WatchedFile`——读取走 getter，自动按文件戳重载。原本散落在 10 处的手动刷新调用变成 0 处，"忘了刷新"这个错误不再可能被写出来。

2. **连错 DSH 实例**：插件靠环境变量猜端口，同机跑第二个 DSH 时连到了**第一个**实例上。
   *修法*：读 `ctx.webServer.port`，也就是 DSH 实际绑定的端口。

3. **控制面板越权（安全漏洞）**：隧道是**从回环重新发起请求**的，所以"仅限本机"的开关接口对远程浏览器也是"本机"。实测中我成功从远程把隧道关掉了。
   *修法*：不是加路径黑名单（那需要在隧道和中转两侧长期维护两份名单），而是**直接不开这个 HTTP 接口**。控制改走文件，由操作系统的 `0600` 权限保证——代理请求根本碰不到文件系统。漏洞连同两处黑名单代码一起消失了。

4. **吊销主机后仍可访问**：写文档时去验证"重启才断开"的说法，发现 revoke 后浏览器仍返回 200。
   *修法*：请求路径上校验并主动断开隧道。

5. **CLI 管道时崩溃**：`status | head` 会让 CLI 抛 EPIPE 堆栈。
   *修法*：在唯一的输出函数和进程级各加一道护栏。

## 兼容性

- Node.js ≥ 20
- DeepSeek Harness `0.1.0-rc.5` ~ `0.1.0-rc.8`
- 隧道只依赖 DSH 的 HTTP 接口，不碰内部服务，所以 DSH 升级一般不会影响它
